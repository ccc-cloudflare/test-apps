# Workers 的 CPU 時間限制

> Cloudflare Workers 的計費單位不是「請求跑了多久」，而是 CPU 時間——程式碼實際佔用 CPU 在算東西的時間。這篇解釋免費方案的 10ms 上限意味著什麼，以及對 Mini-Lang 專家的實際影響。

## 1. CPU 時間和時間的差別

Workers 等待網路（fetch NVIDIA API、等模型吐字）時 CPU 是閒置的，**不計入**限制。計入的是真的在算的時間：解析 JSON、組字串、迴圈。

| 方案 | CPU 時間上限 | 超過會怎樣 |
|---|---|---|
| Free | 每次請求 **10ms** | 回 1102 錯誤（"Worker exceeded CPU time limit"），整個請求被砍掉；**不能調高** |
| Paid（$5/月起） | 預設 30 秒，最高可調到 5 分鐘 | `wrangler.jsonc` 的 `limits.cpu_ms` 可調 |

10ms 聽起來很少，但 CPU 很快：純 JS 計算（例如檢查一段文字是否在 247 字字表內、把 1,236 條詞典組成字串）大約只要 0.1–1ms。

## 2. 對這個專案的實際影響

Worker 每個請求做的事：

| 工作 | CPU 消耗 | 限制內嗎？ |
|---|---|---|
| 解析請求、組系統提示詞 | < 1ms | ✓ |
| 解析 NVIDIA 的 SSE chunk、重新包成自己的事件 | 每個 chunk < 0.1ms，串流幾千個 chunk | ⚠️ 累積起來是風險 |
| `check_minilang`（247 字 + 1,236 條詞典） | < 1ms／次 | ✓ |
| 等模型生成（佔總時間 95% 以上） | 0（都在等網路） | ✓ 不計費 |

實測參考：這種「代理 + 輕度解析」的 Worker，一次長回答的累積 CPU 通常在 5–50ms 之間。**短回答免費方案多半過得了，長回答（模型思考多、輸出幾千字、或反覆呼叫檢查工具）就會撞牆**——而且是在回答到一半時斷掉，使用者只看到串流突然中止。

## 3. wall clock 沒有限制

Free 方案雖然 CPU 只給 10ms，但**整個請求可以掛著很久**：等 GLM 思考 30 秒、串流 60 秒都不會被砍，因為那些時間 CPU 在睡覺。所以這個 Worker 不是「跑不完」，而是「算太多會被砍」。

## 4. 為什麼建議付費方案

- 模型串流回答最長可到 8,192 tokens，每個 token 一個 SSE chunk，每個 chunk 都要 `JSON.parse` + 字串處理；
- 免費方案的 10ms 是硬上限、不能調；
- 付費 $5/月就有 30 秒 CPU（預設），這個 Worker 遠遠用不完，等於買個保險。

另外要注意免費方案的**每天 100,000 個請求**上限——個人使用完全夠，但這個 API 是公開的（有 CORS），被人拿去用很快就會燒完，這也是 README 建議加 rate limiting 的原因。

## 5. 想留在免費方案的優化

1. **減少每個 chunk 的工作**：現在每收到一個 delta 都 `JSON.stringify` + `enqueue` 一次；可以改成小批次（例如每 50ms 或每 N 個 chunk 合併再送），解析次數不變但輸出端省一些。
2. **reasoning 不用逐字轉送**：如果不需要在網頁上顯示思考過程，可以把上游的 `reasoning` 直接丟掉，省下轉送與前端渲染。
3. **前端直接吃上游的 SSE 格式**：讓 Worker 把 NVIDIA 的 chunk 幾乎原樣轉發（只做位元組級的管線傳遞），把解析搬到瀏覽器——但工具循環需要伺服器知道模型是否呼叫了工具，得改成「最後一輪才原樣轉發」的混合模式，比較複雜。

## 6. 免費方案的其他限制（備查）

| 限制 | 免費 | Paid |
|---|---|---|
| CPU 時間 | 10ms | 30 秒（可調到 5 分鐘） |
| 請求數 | 100,000／天 | 依用量計費，含 1,000 萬／月 |
| Worker 大小（打包後） | 3 MB | 10 MB |
| KV 讀取 | 100,000 次／天 | 依用量 |
| 子請求（fetch） | 50 次／請求 | 1,000 次／請求 |

本專案打包後約 0.5 MB、每個請求 1–3 個子請求、KV 只在啟用 PROMPTS 時用到，都不是瓶頸；瓶頸只有 CPU。
